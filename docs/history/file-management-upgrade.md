# 文件管理能力升级开发记录

日期：2026-10-30。正式基线仍为 `v1.8.3` / `a321eb47cf9a5686285d3e78ea4c47c262224073`；本页记录尚未创建正式 Tag 的下一版本候选。

## 原始问题与边界

v1.8.3 支持多级目录和图床单图批量移动，但没有通用的文件/文件夹排序与网盘移动。升级必须保留上传队列局部更新、入队目录冻结、旧 SQLite、ID、Token、Range、统计及四条公开分享路径，且不得部署生产。

研究 Nextcloud、Seafile、Cloudreve 和 SortableJS 后，选择原生前端加本地 SortableJS，不引入框架。目标目录选择器抽象为网盘/图床通用组件；移动利用实体路径与逻辑目录无关的现状，只改数据库关联。

## 失败与修复

首次测试机文件管理脚本在“拖拽后立即下移”处失败。最初的 Toast 等待存在竞态；改为等待网络响应后进一步确认下移请求根本未发出。根因是拖拽保存尚在异步刷新，`moveOrder()` 仍按旧 `S.files` 判断项目位于边界。

修复为 `S.sortPending` Promise 链：所有排序保存串行执行，上下移动先等待前一拖拽保存和局部列表刷新，再重新计算索引。测试也改为等待每次 `/api/items/reorder` 响应，避免复用仍可见 Toast。修复后同一场景通过。

循环移动测试最初预期 HTTP 400；实际批量接口按设计返回 200 并在 `failed[0].reason=cycle` 表达单项失败。测试随后按真实 API 语义校正，目录关系未被修改。

## 验收证据

开发机和重装后的 Debian 12 测试机均为 9/9 HTTP/SQLite 测试通过。真实 HTTPS Chromium 通过：文件夹/文件桌面拖排、上下移动、单文件移动、文件/文件夹混合批量移动、自动重命名冲突、图床文件夹与图片移动、375/390/430px、页面错误 0。

移动前后文件和文件夹分享 URL 不变；公开下载 HEAD 200、Range 206、越界 416，返回内容正确；循环移动明确失败。原上传验收仍保持 710px 滚动、搜索焦点、`.shell` 节点、队列目标目录和三种移动视口。服务重启前后 89 个目录、48 条文件记录和 48 个实体的联合 SHA256 摘要一致，SQLite integrity check 为 ok。

测试服务器使用 InstallNET `yijianDD` commit `326b243c65bbcf63ecd400ac562ec0e4ab7ab98d`，脚本 SHA256 `624efb3e0665e94654310784ba7a32d059a505a49002159ddc0544b3572347c4`，重装为 Debian 12 AMD64。生产服务器和生产域名未连接、未修改。
